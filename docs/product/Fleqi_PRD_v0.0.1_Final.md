# 01｜产品定位与统一口径

## 1.1 产品目标

本产品是开源的文件管理器附属 AI 快捷应用，不替代 Finder、Windows 文件资源管理器或 Linux 文件管理器，也不替代用户日常使用的终端。

P0 的主产品形态不是聊天主窗口、独立文件管理器、全屏工作台或通用桌面 Agent，而是挂在文件管理器窗口底部的小型弹出式外挂窗口。用户的视觉感受应当是“文件管理器下面多了一小块 AI 操作区域”，而不是打开了另一套大型软件。

交互参照 Substage：以当前窗口与文件选区为上下文，通过一个输入框完成聚焦的文件操作。弹出、收起、窗口跟随、提交与结果反馈的体验应高度接近该参考方向；允许加入不增加学习负担的小创新。项目使用自己的品牌、图标与视觉素材，不要求复制对方专有资源。Substage 的官方定位参考见 [R1]。

**首先明确交互方式和逻辑，再进入详细视觉设计**。

## 1.2 两种入口的职责

| 维度 | 底部快捷 Agent | 侧边 PI Agent |
| --- | --- | --- |
| 主形态 | 文件管理器底部的紧凑外挂输入栏 | 唯一一个独立悬浮球，展开为可移动、可贴边的真实终端 |
| 核心任务 | 文件与文件夹方向的快速、明确操作 | 复杂、多步骤、多类型工具调用 |
| 过程展示 | 不展示工作过程、工具日志或思考内容 | 可以展示终端输出、工具执行详情与交互 |
| PI 来源 | 始终使用我们封装并随应用提供的内置 PI；不可切换 | 用户可选择内置 PI 或自己已安装的 PI |
| 功能取舍 | 小而专精，主要使用我们提供的文件工具 | 保留 PI 原有交互，新增重点仅为 MCP、skills |
| 版本 | P0 必须完整交付 | P0 做必要准备，P1 交付实际能力 |

“底部不展示过程”不等于“完全没有反馈”：允许简短的目标确认、必要的补充问题、工作进度、完成结果和错误提示，但不出现长对话、终端滚动日志或逐步推理展示。

原文 P1 / P3 的侧边能力在本稿统一归入后期 P1，不因为编号统一就提前实施。配置隔离与配置迁移仍是不同概念：复制兼容配置后可以继续保持与原环境独立。

## 1.4 围绕 PI 的产品工作方式

**CORE-01｜后端主体**。Agent 任务理解与工具调用以 PI 为主要后端。我们提供文件管理器上下文、集成好的文件工具和面向该场景的交互前端，不以重新实现一套 Agent 引擎为本版目标。

**CORE-02｜文件操作流程**。用户选中文件并输入目标 → 应用将明确的选区和请求交给内置 PI → 模型在 PI 中选择并调用可用工具 → 工具完成文件操作 → 底部显示进度与简短结果。这是产品行为描述，不指定进程、通信或模块设计。

**CORE-03｜真实能力边界**。实际可执行范围由模型能力、已提供工具、所需依赖与系统权限共同决定。不能仅因为模型会描述某个操作就宣称已经支持，也不能把产品简化成只转发一句提示词、不检查目标和结果的输入壳。

**CORE-04｜交互与执行解耦**。底部隐藏工作细节，侧边可以显示终端详情；两者都围绕 PI 工作，但不因此强制共用同一会话、插件集合或运行配置。切换侧边 PI 不改变底部的集成状态。

# 02｜版本范围

## 2.1 P0：先完成 macOS 权限与底部快捷体验

P0 的首个交付平台为 macOS。第一优先级是“必要权限申请与复检 → Finder 窗口和选区 → 底部输入 → 内置 PI 操作文件 → 真实进度与结果”，而不是先交付侧边终端、全套插件管理或通用聊天窗口。

P0 必须完成：应用内置 PI、权限用途说明与授权引导、权限实际生效验证、底部外挂窗口、输入和选区上下文、首批文件快捷能力、真实进度与结果、模型和登录配置、菜单栏入口，以及底部启停控制。

P0 为后期侧边保留必要的产品连续性：内置 PI 可继续使用，已有账号、模型配置和任务信息不需无理由重建；可预留侧边开关与状态，但尚未提供的功能不得显示为可用。本文不要求先实现完整侧边，也不规定“框架”如何写。

**排期细化基线**：外部 PI 的检测、来源选择、用户插件迁移和复杂扩展管理，按其实际用途随 P1 侧边能力完成，不作为第一批底部体验的前置条件。P0 的内置 PI 及必要工具必须独立可用，不等待用户安装或迁移 PI。

## 2.2 P1：后期的单球终端与复杂任务

P1 交付唯一一个独立悬浮球、完全藏球后的黑色箭头、拖出球与双击展开两条不同交互、贴边终端、真实 PI 终端输入与输出、PI 前端定制、内置或用户 PI 的选择、兼容配置迁移与冲突处理、MCP 和 skills，以及底部任务的转交。

侧边是底部体验的补充，不是底部运行的依赖。侧边关闭、外部 PI 不可用或侧边迁移失败时，不得连带让底部快捷栏失效。P1 不新增 IDE、全能工作台或复杂多 Agent 调度平台。

平台顺序与功能优先级是两条约束：平台按 macOS、Windows、Linux 推进；功能先底部、后侧边。首个验收里程碑固定为 macOS 的 P0，其他平台最低版本和后期具体排期另行细化。

## 2.3 范围标识

文中“必须”表示由用户明确提出或为了兑现该交互必需的需求。“补充基线”表示本次将模糊描述细化成的可执行默认规则，可在评审中调整。“候选”不构成 P0 验收承诺。

# 03｜P0：底部快捷栏的交互需求

## 3.1 挂载、唤起与窗口行为

**P0-UI-01｜附属窗口**。快捷栏挂在当前关联的文件管理器窗口下边缘，保持小型、紧凑的视觉比例。不另建文件列表，不替代原窗口，不将用户带入大型聊天界面。宽高、边距、圆角与阴影在 UI 阶段确定。

**P0-UI-02｜快捷唤起**。必须提供快捷唤起和收起方式，并可从菜单栏或托盘重新打开。默认快捷键、是否随文件管理器激活而自动出现，留待交互评审；唤起界面不应等待模型响应。

**P0-UI-03｜窗口跟随**。在声明支持的平台环境内，Finder／文件管理器放大、还原、移动、缩放或切换前台窗口时，快捷栏应跟随正确窗口。不能停留在无关应用下面，也不能从错误窗口读取选区。

**P0-UI-04｜边界状态**。关联窗口最小化、关闭或不再可见时，快捷栏不得孤立悬挂。多屏、缩放变化和屏幕下缘空间不足时，应保持输入区可见；具体停靠补偿方式在 UI 评审中确定。运行任务不因窗口暂时不可见而被默默取消。普通窗口放大与系统原生全屏、桌面空间切换分别验证；不将前者通过等同于全部全屏行为已支持。

**P0-UI-05｜动画与焦点**。弹出、收起、进度和结果切换应自然连贯。用户唤起后可立即输入；快捷栏收起后不应长期抢占文件管理器焦点。应兼容键盘操作和中文输入法，具体键位后续确定。

## 3.2 输入与文件上下文

**P0-CTX-01｜自然语言输入**。用户直接输入目标，例如“把这些图片转成 JPG”“文件名加上今天的日期”。默认不要求用户掌握命令行、工具名或复杂参数。

**P0-CTX-02｜操作对象**。支持单选、多选、文件夹及当前目录。输入栏应以简短提示说明正在处理的对象或数量，让用户知道“这些文件”指的是哪些文件。

**P0-CTX-03｜无选区时的规则**。创建文件可使用当前目录；需要现有文件的操作应要求选择对象。不得将“没有选中”自动解释成“递归处理整个目录或整个磁盘”。

**P0-CTX-04｜提交后的目标固定**。任务提交时确定操作对象。用户随后改变选区、切换标签页或打开其他窗口，不得悄悄改变已经提交的任务目标。源文件消失、被改名或不再可访问时，应明确反馈。

**P0-CTX-05｜简短澄清**。请求缺少关键参数或具有明显歧义时，只问完成任务所必需的问题。例如“压缩一些”可以询问目标大小或质量；不展开长篇计划讨论。

## 3.3 状态与操作流程

默认流程为：关联窗口和选区 → 输入目标 → 必要时补充或确认 → 执行 → 显示进度 → 展示简短结果 → 继续输入或收起。

| 状态 | 底部栏展示内容 | 允许的操作 |
| --- | --- | --- |
| 待输入 | 输入框、简短对象提示 | 输入、提交、收起 |
| 等待响应 | 简短等待状态与活动指示 | 取消、收起 |
| 待补充／待确认 | 一个聚焦的问题或影响提示 | 补充、确认、取消 |
| 执行中 | 进度条、状态、可用时的完成数量 | 取消、收起 |
| 完成 | 成功数量或简短查询结果、结果入口 | 定位结果、复制结果、继续操作 |
| 部分完成 | 已成功与未完成数量、简短原因 | 查看失败对象、确认后重试 |
| 失败／已取消 | 明确状态及下一步 | 修改请求、重试、定位已有产物 |

**P0-FB-01｜真实进度**。能获得真实百分比时显示进度条；只能知道项目数量时显示“已完成 4 / 12”；暂时无法获知进度时使用不定进度指示。不得让随机增长的百分比冒充真实执行进度。

**P0-FB-02｜不展示过程**。底部不显示终端命令、工具调用明细、逐步分析、长日志或思考内容。诊断信息可在菜单入口中查看；P1 的详细工作过程由侧边终端承载。

**P0-FB-03｜必要确认不是工作过程**。覆盖、移入回收站、大范围修改、外发文件等操作需要简短明确的确认。普通低风险任务不必都经过复杂审批。P0 不要求做完整命令模拟器、可视化流程图或大型预览台。

**P0-FB-04｜取消与结果**。取消后不得继续启动新的后续动作；已经完成的部分必须如实说明，不能声称一定撤销。完成时提供定位输出目录、打开产物或复制查询结果的轻量入口。

**P0-FB-05｜任务数量**。补充基线：P0 以一个清晰的前台快捷任务为主，不强制加入复杂队列或并行工作台。批量文件可以属于一个任务。忙碌时不得无反馈地接受第二个请求。

## 3.4 简单任务与复杂任务的边界

“简单”按目标和交互复杂度区分，不只按文件数量或内部调用次数区分。“把 100 张图片缩小后打成一个 ZIP”仍可作为目标明确的快捷任务；需要持续讨论、跨多种外部服务、动态探索或反复人工干预的工作应转到侧边。

P0 没有侧边能力时，对超出范围的任务直接说明当前不支持，不假装已经转交。P1 可以提供“在侧边继续”，但必须由用户确认，不得自动展开终端并执行新任务。


## 3.5 输入、范围与异常边界补充

以下为验收所需的补充基线，不增加新的主界面或通用 Agent 能力。

**P0-EDGE-01｜输入法与重复提交**。中文输入法选词所用的回车不能误提交任务；重复按键、按钮连点或界面重绘不应重复执行同一批文件操作。

**P0-EDGE-02｜特殊选区**。不同目录、不同磁盘、只读文件、失效路径、符号链接以及虚拟或搜索视图应分别识别。无法取得明确文件对象时提示限制，不凭显示名称猜测路径；递归处理必须有明确范围，不因链接而扩到未授权位置。

**P0-EDGE-03｜路径与资源保护**。中文、空格、引号、长路径及命令符号是文件名的一部分，不能变成额外命令。压缩包解压不得写出用户指定目标范围；异常递归、异常解压量和磁盘空间不足应可停止并反馈。

**P0-EDGE-04｜无静默重跑**。连接中断、超时、进程退出或应用异常重启后，不能自动重复可能已经完成的改名、移动或删除。能确认的完成状态如实展示；不能确认时明确标记并让用户决定后续操作。

# 04｜P0：访达 + AI 的能力清单

## 4.1 功能范围原则

下表保留此前讨论的“文件管理器 + AI”能力范围，不是宣称 Substage 的全部功能都要进入首版。能力以当前选区或明确目录为中心，优先覆盖高频文件操作；同一自然语言入口可以调用多个小工具，但底部仍保持轻量形态。

其中“P0 基础”作为本稿建议的首版最小基线；“plan 锁定范围”表示开发 Agent 应在计划阶段提出并记录具体动作、格式与依赖，不能把类别名称当作全部变体已承诺。“后期候选”只保留方向，不阻塞 P0 发布；对建议基线的增减需在 plan 中说明，不能静默删减。

| 能力类别 | P0 基础／建议最小范围 | 典型输入 | 延后或需明确的范围 |
| --- | --- | --- | --- |
| 文件与文件夹操作 | 新建、复制、移动、重命名、按要求放入子目录、移入回收站 | “新建一个导出文件夹，把这些文件复制进去” | 永久删除、系统目录修改不作为默认快捷操作 |
| 批量命名 | 前后缀、编号、替换词、日期、大小写处理；同名冲突提示 | “按顺序改为项目名_001、002……” | 依赖复杂内容理解的自动命名为 后期候选 |
| 目录整理 | 对明确范围按类型、日期或用户规则分类；创建需要的目录 | “把选中的文件按类型分文件夹” | 不默认扫描全盘，不自动修改未授权范围 |
| 压缩与解压 | ZIP 打包、解压、查看基本内容；目标位置与冲突处理 | “把这些文件打成一个 ZIP” | 其他压缩格式、分卷、加密等plan 锁定范围 |
| 图片处理 | 常见格式转换、缩放、压缩、旋转；保留原件 | “转为 JPG，最长边 1600 像素” | 建议先锁定 PNG / JPG / WebP；HEIC、ICO、裁剪、元数据清理为plan 锁定范围项 |
| 音频与视频 | plan 锁定范围：常见格式转换、压缩、提取音频、基础裁剪 | “提取视频里的音频” | 不包含专业剪辑台；具体格式、编码与字幕能力单独确认 |
| PDF 处理 | plan 锁定范围：合并、拆分、提取指定页面、旋转、基础压缩 | “合并这三个 PDF” | OCR、复杂排版编辑、加密 PDF 的处理规则单独确认 |
| 文本与文档 | 新建 TXT / Markdown；plan 锁定范围：读取文字、简短摘要、简单文档转换或 DOCX 创建 | “在这里新建一个说明文档” | 不将任意 Office 文档高保真互转视为默认承诺 |
| 信息查询与检索 | 文件大小、类型、数量、路径、时间；按名称、类型、大小筛选 | “找出这个目录里最大的五个文件” | 哈希、重复文件检测、内容检索为plan 锁定范围项；检测不等于自动删除 |
| 打开与结果交付 | 打开文件或目录、定位生成文件、复制路径和文本结果 | “打开刚生成的文件夹” | 打开外部终端可列为候选，不把底部改成终端 |

## 4.2 每类能力的共同要求

**P0-CAP-01｜确定支持范围**。发布前必须列明已验证的动作、输入与输出格式、需要的依赖、平台差异。不把“模型知道某个命令”当作该功能已支持；未列入清单的格式必须给出可理解的限制。

**P0-CAP-02｜不替用户改目标**。转换失败时，不得只修改后缀冒充转换成功。无法达到指定大小、页码或输出数量时，应说明未达标，而不是只报告命令执行结束。

**P0-CAP-03｜保留与冲突**。补充基线：转换默认保留原件，输出位置可见；覆盖与同名冲突需有清楚规则。批量改名和移动应记录本次变化；仅在确实可恢复时提供撤销，不承诺万能撤销。

**P0-CAP-04｜依赖缺失**。缺少转换工具、模型或权限时，说明缺失项与处理入口。额外下载、安装或较大的依赖获取需要告知用户，不静默修改用户环境。

**P0-CAP-05｜结果核验**。至少核对产物是否存在、目标位置与格式是否符合请求，并区分成功、部分成功、失败。具体业务检查规则随动作补充，不在本稿指定实现方式。

# 05｜PI 来源与配置：P0 内置，P1 外部选择及迁移

## 5.1 内置 PI 的产品要求

**P0-PI-01｜随软件提供**。软件包含我们封装的 PI。没有自行安装 PI 的用户，也能完成首次配置并使用底部快捷栏，不要求先到终端安装官方 PI。

**P0-PI-02｜底部固定内置**。底部始终使用项目封装、集成好的 PI，配置页不得出现“切换到用户 PI”选项。底部使用我们提供的文件工具与限定能力范围，不因为 PI 可以扩展，就默认开放任意用户插件或复杂工作流。

**P1-PI-01｜选择只属于侧边**。侧边启用后，用户可以选择内置 PI 或自己已安装的 PI。该选择仅影响侧边终端；底部不替换 PI，不读取外部 PI 的配置作为默认来源。选择结果可在侧边设置中更改。

**P0-PI-04｜不破坏现有环境**。软件安装、升级、退出或卸载，不应擅自卸载用户原有 PI、覆盖其配置或删除其插件。

## 5.2 P1：用户 PI 检测与选择流程

首次启用侧边终端或用户主动打开其设置时，检测是否存在用户已安装的 PI；识别失败时允许用户指定有效的安装位置。应说明识别到的 PI 来源、可用状态以及配置来源；不要求用户在多个含糊选项间盲选。

| 选择模式 | 底部快捷栏 | P1 侧边终端 | 配置行为 |
| --- | --- | --- | --- |
| 无外部 PI | 内置 PI | 内置 PI | 使用本应用的默认配置 |
| 内置 PI，保持独立 | 内置 PI | 内置 PI | 不迁移外部配置，原环境不变 |
| 内置 PI，迁移已有配置 | 固定内置 PI，默认文件配置不变 | 内置 PI，导入兼容用户配置 | 迁移主要用于复现侧边使用习惯；不自动改变底部工具范围 |
| 使用用户已安装的 PI | 内置 PI | 直接调用所选外部 PI | 保留用户现有 PI 的配置和工作习惯，不强行改装 |

“直接调用外部 PI”与“把配置复制进内置 PI”是两个不同选项，不能在用户选择其中一个时偷偷执行另一个。

## 5.3 P1：配置迁移范围

选择在侧边使用内置 PI 并迁移配置后，先读取并展示可迁移内容，经用户确认再执行。目标是在内置 PI 的侧边使用中尽量复现原有插件、skills 与偏好，同时保留我们的功能；不是复制全部文件，也不是把底部替换成用户 PI。迁移不自动使全部插件在底部生效。

| 配置类型 | 迁移要求 |
| --- | --- |
| 插件／扩展包 | 识别来源、版本、依赖与启用状态；复制或安装兼容项；记录跳过或失败原因 |
| Skills | 迁移可兼容的技能、引用资源和必要路径；失效路径应提示修正 |
| 自定义指令与快捷键 | 保留兼容配置；与已有注册项冲突时进入冲突处理 |
| 提示词与偏好 | 迁移可兼容模板、用户规则及偏好；不得覆盖底部快捷栏的固定产品边界 |
| 模型与服务配置 | 迁移服务地址、协议、模型标识等可兼容设置，迁移后提供连接测试 |
| MCP 配置 | 保留可识别的服务配置及启用意图；实际调用在支持该能力的阶段启用 |
| 主题与终端相关配置 | 对侧边终端兼容的部分尽量保留；不强行改变底部产品 UI |
| API Key、登录态等凭据 | 单独说明并征得授权；不可默认混入普通配置复制或诊断输出；不能复用时重新授权 |

会话历史不作为 0.0.1 默认迁移要求。迁移报告应包括成功、重复跳过、不兼容、缺失依赖和需要用户处理的项目。失败应可重试；迁移前后的本应用配置应可恢复。

迁移不等于持续同步。0.0.1 默认在用户主动触发时重新检查并合并，不静默追踪和双向修改两个环境。

## 5.4 P1：注册状态与冲突处理

**P1-MIG-01｜分类准确**。区分“未安装”“已安装但未注册”“已注册”“被禁用”“加载失败”和“不兼容”。不能把未注册一概当成缺少安装包而反复安装。

**P1-MIG-02｜完全重复**。来源、标识、版本和内容均相同的重复项自动跳过，保持迁移幂等；重复运行不应不断增加相同插件。

**P1-MIG-03｜真实冲突**。不同插件注册同名指令、工具或快捷键，或相同插件版本不兼容时，展示冲突项及影响，让用户选择保留哪一个。不能只凭显示名称相同就删除插件。

**P1-MIG-04｜自动修复边界**。可以自动去掉完全重复的注册、阻止冲突配置进入本应用的正常启动状态，并暂时隔离导致失败的迁移项。涉及两个不同插件的取舍，不得未经确认随机卸载。

**P1-MIG-05｜卸载范围**。用户确认后，可以禁用或卸载本应用管理环境中的冲突项，再验证 PI 能否启动。直接使用外部 PI 时，默认只诊断并提示；修改用户原环境需要额外明确授权。

**P1-MIG-06｜保留核心能力**。用户配置不得静默替换底部的必要工具与限制。会破坏底部快捷体验的插件可以迁移保存，但应标记为仅供侧边使用或暂不启用，并说明原因。这是对“尽量复刻用户 PI”和“底部必须轻量”的取舍规则。

## 5.5 底部入口与单个侧边入口独立开关

底部快捷栏与唯一一个侧边悬浮入口必须独立控制；“两个入口”不代表两个悬浮球。P0 先提供底部开关，以下完整组合在 P1 侧边可用后验收。只开底部、只开侧边、两者都开、两者都关均应具有明确行为；两者都关闭时，菜单栏／托盘仍可用于恢复入口。

“收起窗口”只改变可见性，不等于终止任务；“关闭某个入口”停止自动唤起，但不能默默丢弃正在执行的任务；“退出应用”需要说明运行任务将如何处理。涉及任务终止时应提供明确选择。

# 06｜P0：模型、登录、权限与菜单入口

## 6.1 Codex auto 登录

**P0-AUTH-01｜需求解释**。保留用户原称“Codex auto 登录”；本稿暂按“支持可用的官方账号授权流程，并在授权有效时继续使用已有登录状态”理解，而不是自动填写账号密码或跳过首次授权。

**P0-AUTH-02｜交互**。提供登录、登录状态、失效提示、重新授权和退出登录入口。可复用的凭据必须经过授权与兼容性检查；不能复用时明确要求重新登录。

**P0-AUTH-03｜验收边界**。实际接入方式、第三方 PI 的适配、可用模型与账号权限需要在实施时验证。支持普通 API Key 不能代替完成此项需求；也不能仅因机器里存在 Codex 配置文件，就宣称可无条件接入。

术语依据：OpenAI 官方文档区分 ChatGPT 账号登录与 API Key 登录，并说明登录缓存、自动刷新及凭据保护要求；这些事实不等于任意第三方应用都已获得同样的接入资格。[R3]

## 6.2 自定义服务与协议

**P0-MODEL-01｜自定义连接**。支持自定义 API 地址、API Key、模型标识、连接名称与协议类型。提供保存、编辑、测试和切换；不能把模型或供应商写死在界面中。

**P0-MODEL-02｜多协议目标**。不局限于 OpenAI 兼容接口。补充基线：协议验收清单至少明确 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Google Gemini 对应接口，以及选定 PI 版本已有的其他适配范围。具体覆盖清单必须在实施前确认。

**P0-MODEL-03｜诚实声明支持**。“支持不同协议”是持续可扩展的需求，不写成“所有未知协议无条件兼容”。不支持的协议应提示缺失适配，不能只填入不同地址就宣称已支持。

**P0-MODEL-04｜本地服务**。允许配置已运行的兼容本地模型端点，不把模型下载、训练或本地模型管理平台列为 P0 必做内容。

**P0-MODEL-05｜作用范围**。应用设置必须说明影响底部、内置侧边 PI 还是所选外部 PI。对用户外部 PI 的配置，不得静默覆盖；切换模型不应悄悄改变运行中任务的服务来源。

Pi 官方资料列出多供应商、自定义模型和扩展能力；Fleqi 的实际协议、字段和模型特性必须按采用版本验证并记录，不直接继承网页宣传中的全部支持范围。[R2][R4]

## 6.3 思考与展示开关

**P0-THINK-01｜推理设置**。提供是否启用推理／思考的设置；模型支持多个强度时，可以提供相应档位。模型无法关闭思考或不提供该参数时，应显示实际限制，不用“低强度”假冒“完全关闭”。

**P0-THINK-02｜展示设置**。“思考链是否展示”整理为“是否展示模型公开返回的推理摘要或可见思考内容”。不要求获取、恢复或伪造模型未公开的内部推理。

**P0-THINK-03｜底部优先规则**。即使全局开启展示，底部快捷栏仍不展示工作过程或思考内容。该展示设置仅在 P1 侧边终端及其支持的模型／PI 来源中生效。

## 6.4 macOS 权限申请、状态与实际生效验证

**P0-PERM-01｜权限是首个验收重点**。首次配置先列明本版本实际需要的全部权限、用途、影响与当前状态，引导用户按系统流程授权，再检查是否真正生效。“申请所有权限”指本版本文件操作与窗口交互需要的全部权限，不是索取无关的相机、麦克风、通讯录等访问。

macOS 的辅助功能、完全磁盘访问等权限由系统与用户授权管理；随软件封装 PI 不代表已经获得权限。辅助功能、自动化、文件与文件夹访问也是不同类别，不能用一个“已授权”标识混为一谈。[R5][R6]

| 权限或检查项 | 本版要求 | 通过条件与失败处理 |
| --- | --- | --- |
| 完全磁盘访问 | 纳入 macOS 权限配置与检查清单，说明文件访问用途 | 授权指引完成后验证实际执行环境；不能把普通临时目录可写误报成完全磁盘访问已验证 |
| 辅助功能 | 纳入窗口交互所需权限清单 | 检查关联窗口与必要辅助操作是否可用；拒绝、撤销或失效要明确提示 |
| 自动化／Finder 控制 | 仅在最终选区或控制方式实际需要时申请 | 分别验证所需 Finder 交互；不假定辅助功能已授权就自动包含本项 |
| 文件与文件夹访问 | 根据实际文件位置、所采用方式与系统要求检查 | 区分目标目录不能访问和模型／工具失败，不反复假执行 |
| 其他权限 | 实现中确实需要才列入，并说明原因 | 屏幕录制、输入监控等不因“做悬浮窗”就默认列为全量必需权限 |

**P0-PERM-02｜完整授权流程**。检查 → 展示用途和缺失项 → 引导系统授权 → 返回应用复检 → 必要时提示重新打开相关功能 → 验证窗口上下文与文件操作 → 标记就绪或受限。系统不提供直接弹窗的权限，应给出设置指引，不伪造授权弹窗或自动批准。

**P0-PERM-03｜状态必须可辨**。区分未申请、未授予、等待用户处理、授权后待验证、已验证可用、被撤销／失效，以及当前无法可靠判断。只有该版本实际必需项全部通过时，才能显示“所需权限检查通过”；可选且不适用的权限应显示“不需要”，不能冒充已授予。

**P0-PERM-04｜验的是执行链，不只是页面**。检查真实操作文件的内置 PI 及其所调用工具是否能够完成任务，不只检查应用设置页。不能假定主应用、内置 PI 和后期用户 PI 的权限状态天然一致；P1 启动外部 PI 时对该执行环境另行验证。

**P0-PERM-05｜非破坏性功能自检**。至少验证当前 Finder 窗口及选区可获取，并通过内置 PI 在用户允许的测试位置完成临时文件的新建、读取、改名和清理。需要验证受保护位置时，应在用户允许范围内进行最小访问检查。不得为测试权限改动用户真实文件，不将一次测试成功扩大为“所有路径永远可操作”。

**P0-PERM-06｜拒绝与撤销**。缺少必要权限时，明确限制受影响的功能，并保留设置、重新检查和退出入口。用户拒绝后不循环弹窗；应用更新、重新安装、权限撤销或执行失败后能够重新检查。部分授权不能报告全部就绪。

## 6.5 Windows／Linux 权限与数据边界

**P0-PERM-07｜按平台先后验证**。macOS 的权限与底部体验先通过；随后 Windows 单独验证普通用户环境、目标目录访问、必要提权及拒绝后的表现；Linux 最后按实际支持的桌面与文件管理器验证。不沿用 macOS 权限名称，不以“管理员身份启动”代替逐项验证。Windows 的标准权限与 UAC 提权具有独立流程。[R7]

**P0-PERM-08｜任务范围不扩大**。获得磁盘访问能力不等于每次任务都可扫描全盘。模型通过 PI 操作的范围仍受用户请求与明确选区约束；文件内容、插件说明和读到的文档不能自动转化为扩大权限的授权。

**P0-PERM-09｜数据与凭据**。应说明使用云模型时可能外发的路径、文件内容和工具输出，提供可理解的选择。密钥与登录态不得进入普通日志；收集诊断信息时避免带出用户文件内容。

## 6.6 菜单栏／托盘

**P0-MENU-01｜常驻入口**。macOS 使用菜单栏图标；Windows 及适用的 Linux 桌面提供对应的托盘入口。不能提供托盘的环境，须保留其他可恢复入口，不允许关闭面板后无从找回应用。

菜单内容至少包括：显示／隐藏底部栏；侧边入口的开关与可用性；模型与登录设置；侧边专用的 PI 来源及配置迁移（P1）；权限检查；最近任务的简短结果及诊断入口；其他已支持工具；退出应用。MCP 与 skills 的具体管理入口在 P1 可用时启用。

# 07｜P1：侧边浮动终端

## 7.1 唯一悬浮球与三种可见形态

**P1-UI-01｜只有一个**。整个应用只提供一个独立的侧边悬浮球，可移动到支持的停靠位置。拖动、换边、显示器切换或切换 PI 来源都不能生成第二个球或重复会话入口。

**P1-UI-02｜本体是终端**。展开后是用户参考照片所指的真实终端形态，内部运行 PI，并提供 PI 的交互输入与具体输出。收起后变回球；球继续向默认右侧边缘拖入后完全隐藏，只保留黑色箭头。不是一个只显示聊天气泡的面板。

| 状态 | 屏幕上显示什么 | 是否展示终端交互 |
| --- | --- | --- |
| S0：入口关闭 | 不显示球、箭头或终端；菜单入口可重新开启 | 否；关闭入口与终止任务分开处理 |
| S1：悬浮球 | 一个可拖动的独立球，默认收缩形态 | 否 |
| S2：贴边箭头 | 球体完全不可见，仅留朝屏幕中央的黑色箭头 | 否 |
| S3：终端展开 | 可输入、显示 PI 详情的真实终端窗口 | 是 |

首次启用侧边以 S1 球形态出现，不自动强制弹出大终端。普通“收起终端”回到 S1；进入 S2 需要进一步贴边隐藏。

## 7.2 手势与状态转换

| 起始状态 | 用户动作 | 目标状态与要求 |
| --- | --- | --- |
| S1 悬浮球 | 点击球 | 连贯展开为 S3；输入区可交互 |
| S1 悬浮球 | 在屏幕内拖动 | 球随手移动，保持 S1 |
| S1 悬浮球 | 继续向最右边缘拖入 | 球完全退出可见区域，进入 S2；右侧只留向左的黑色箭头 |
| S2 箭头 | 按住并向屏幕内侧拖动 | 拉出球，回到 S1；不自动展开终端 |
| S2 箭头 | 连续双击 | 动画表现为箭头拉出球、球继续展开成 S3；一次双击完成，无需第三次点击 |
| S3 终端 | 点击收起 | 收回同一个球，进入 S1；不默默结束 PI 会话 |
| 任一可见状态 | 关闭侧边入口 | 进入 S0；运行任务另行提示和处理 |

**P1-UI-03｜拖动与双击不同**。拖动用于取回球、重新摆放；双击用于直接进入 PI 输入。不能将两者都实现为“打开终端”，也不能以单击展开取代用户指定的双击。补充基线：单击箭头仅作轻量反馈，不提交任务、不展开终端。

**P1-UI-04｜连续动画**。双击箭头的动画必须把“藏在边缘 → 球出现 → 终端展开”表现为同一个对象的连续变化，而非突然另开一个无关窗口。动画过程中重复点击或拖动，不应重复启动 PI 或产生多个终端。

**P1-UI-05｜输入焦点**。展开完成后用户可以直接在 PI 交互区输入；中文输入、复制粘贴与中断不受外层动画干扰。收起后焦点应合理回到之前应用。

## 7.3 贴边、移动与会话保持

**P1-UI-06｜停靠边缘对齐**。默认以右侧为主；用户将其放到左侧或顶部时，展开终端按所选边缘贴合。右侧停靠时面板右边贴屏幕右侧、向左展开；左侧停靠时左边贴左侧、向右展开；顶部停靠时上边贴顶部、向下展开。以系统允许的可用显示区域为边界，不将输入区展开到屏幕之外。

**P1-UI-07｜箭头朝内**。右侧箭头明确为黑色、向左指向屏幕中央；左侧和顶部停靠采用对应朝屏幕内的方向。深色背景下需要维持可见性，但不改变用户指定的黑色箭头主体。具体尺寸、命中区域与对比衬底留待 UI 设计。

**P1-UI-08｜移动与尺寸**。球可移动，展开终端也应保留简单的移动及合理尺寸调整能力。贴边展开时不得在屏幕边缘与面板之间留下无意义的浮空偏移。多屏、显示器断开或分辨率变化后，入口必须可找回；不为每个屏幕自动新建球。

**P1-UI-09｜会话保持**。S1、S2、S3 是同一侧边功能的不同可见状态。球被藏起或终端收起，不等于任务取消或 PI 重启；重新展开恢复当前会话。切换 PI 来源、关闭入口和退出应用涉及运行任务时，必须明确提示后果。

**P1-UI-10｜边界测试**。系统原生全屏、桌面空间、顶部安全区域和显示器边界应分别验证；本版不新增刘海专属 UI，也不承诺绕过操作系统窗口限制。具体已知差异必须写入支持说明。

## 7.4 终端与 PI 前端

**P1-TERM-01｜真实终端交互**。终端应支持 PI 所需的文字输入、中文输入法、颜色与布局、滚动回看、复制粘贴、键盘交互、尺寸变化及中断操作。不能只把文本输出贴进一个不能交互的展示框。

**P1-TERM-02｜定制范围**。我们可以修改或重做 PI 在终端内的前端，也可以利用社区现成的终端渲染方式，再叠加侧边浮动面板。此处是允许的产品实现方向，不在本文指定渲染库或代码组织。

**P1-TERM-03｜内置与外部的区别**。内置 PI 可以使用我们定制的前端；直接调用用户 PI 时，应优先保留其可用交互和配置。无法兼容定制外观时允许使用其原有终端界面，不擅自修改用户安装。

**P1-TERM-04｜过程可见**。侧边可显示详细输出、工具调用情况、错误、必要确认及后续问题。模型公开返回的推理摘要可受展示开关控制，但不伪造未提供的内容。

**P1-TERM-05｜保持简单**。终端用于承载 PI 及相关快速工作，不把重做完整终端生态、复杂标签页系统、SSH 管理器或 IDE 列为本阶段目标。

## 7.5 MCP 与 skills

**P1-EXT-01｜MCP**。支持添加、选择、启用、禁用和测试 MCP 配置；展示连接状态与失败原因。需要凭据或启动外部程序时，应让用户知道具体影响。迁移而来的配置只有在确认兼容并启用后才可调用。

**P1-EXT-02｜Skills**。支持识别、导入和使用兼容 skills，并能控制启用状态；缺少依赖、资源路径失效或指令冲突时，进入明确的处理流程。不得把“已复制技能目录”当作技能已能运行。

**P1-EXT-03｜新增能力克制**。以 PI 原有能力为基础，主要增加 MCP、skills 的接入与产品化管理；不默认扩展为多 Agent 平台。底部仅开放适合文件快捷场景、经过启用的部分能力。

外部能力边界：Pi 官方将 skills 列为扩展方式，也将 MCP integration 列在可通过扩展构建的能力中。Fleqi 的需求是“复用并管理 skills、提供可验证的 MCP 接入”，不假设采用的 Pi 版本已默认完成全部集成；具体以锁定版本核验。[R2]

## 7.6 与底部快捷栏衔接

**P1-LINK-01｜转交信息**。用户选择“在侧边继续”后，应保留原始需求、已确定的文件对象、当前目录、已完成操作及尚未完成部分。不得重新读取变化后的选区，导致任务处理错对象。

**P1-LINK-02｜避免重复执行**。转交不应重跑已经完成的文件操作。侧边开始前应能识别任务当前状态，必要时让用户确认继续范围。

**P1-LINK-03｜反向使用**。用户也可以直接在侧边输入“更改文件格式”等简单任务。相同任务的文件保护和结果规则应一致，但侧边仍可以展示过程，底部仍保持简洁。

**P1-LINK-04｜兼容性提示**。侧边选择外部 PI 且无法接收某些上下文、权限或自定义工具时，应明确提示，不能承诺与内置 PI 完全无差别。

# 08｜平台顺序、Rust 与开放边界

**PLAT-ORDER｜已确认平台顺序**。macOS → Windows → Linux。首个平台不是 Windows，也不是三端同时首发。macOS 首先完成所需权限的申请引导、状态复检与实际操作验证，再打磨 Finder 底部体验。

| 顺序 | 平台目标 | 该阶段重点 |
| --- | --- | --- |
| 1 | macOS / Finder | 权限检查和实际生效；窗口放大、还原、移动与底部跟随；选区和内置 PI 文件操作 |
| 2 | Windows / 文件资源管理器 | 独立验证系统权限、选区读取、窗口附属体验与文件工具，不把 macOS 权限逻辑照搬 |
| 3 | Linux / 明确列出的文件管理器 | 按桌面环境逐项验证入口、选区、挂靠和权限，公开差异与限制 |

**P0-PLAT-01｜明确支持环境**。发布前必须列出实际支持的系统最低版本、文件管理器、窗口挂载方式、选区读取能力和已知限制。三平台顺序已经确定；最低版本及 Linux 支持组合仍需具体化。

**P0-PLAT-02｜不能偷换形态**。“底部附属窗口”是核心目标。某环境无法实现同等挂载时，必须说明差异并提交替代交互决策；不能悄悄改成独立大窗口后宣称完全一致。

**TECH-01｜Rust 优先，PI 为后端主体**。使用 Rust 作为本应用优先开发方向，Agent 能力主要围绕 PI 集成。Rust 要求不扩写为“把 PI、所有工具或终端渲染器全部重写”。具体技术组合交由后续开发 Agent 决定。

**OPEN-01｜开源**。正式产品名为 Fleqi，建议仓库名为 `fleqi`；不另设中文正式名称。项目以开源软件为方向。许可证、发行方式和依赖分发安排由后续 plan 明确；名称检索不代表仓库、组织名或域名已经注册。

本文只约定用户获得的能力、行为、边界与验收，不包含系统架构图、进程模型、模块与 crate 划分、通信协议、数据库、UI 框架、渲染库选型或实现代码。

**QUALITY-01｜轻量体验可测**。唤出和收起界面不等待模型；输入、动画和进度不被文件处理阻塞。plan 应分别提出界面响应、任务开始延迟、安装包、内存和批量文件处理的测试方法，再按实测设阈值，不预先承诺未经测量的数值。

**QUALITY-02｜本地界面与依赖**。中文输入和文件名必须正常；关键入口支持键盘操作，状态不只依赖颜色表达。界面的简洁不等于隐去依赖：需要额外工具、模型或网络服务时，明确来源、安装影响、许可和失败恢复，不能把下载后的总占用藏在“轻量”宣传中。

**QUALITY-03｜发布验收不靠截图**。每个“已支持”条目都需要对应系统环境、真实输入文件、调用结果和异常用例。截图或生成式 UI 参考只证明设计意图，不证明权限、文件结果或终端交互已经通过。

| A1-12 | 会话和独立开关 | 球、箭头和终端复用当前会话；入口可独立开关；隐藏不等于取消任务 |
| A1-13 | 底部转交 | 由用户确认，保留文件与任务状态，不重新执行已完成动作 |
| A1-14 | 多屏与权限差异 | 入口始终能找回；用户 PI 所需权限单独验证，不假定继承内置 PI 的授权 |
